## Cross-Section Technical Consistency Review

The single most damaging class of problems here is that the six sections do not share a vocabulary. The schema section defines one set of enums/tables; the RBAC, arch, domain, and design sections each invent their own divergent names. RLS policies are written against columns and tables that the schema does not contain. Below is the prioritized list.

---

**1. [CRITICAL] RBAC's core patient-visibility policy references a column that does not exist in the schema.**
The RBAC section's linchpin helper `can_access_patient()` queries `schedule_sessions s WHERE s.patient_id = p_patient AND s.employee_id = auth.uid()` — visibility via a scheduled session. But the schema section explicitly designed a *separate* table `patient_assignments` as "the RLS backbone" and states under patients: "Employee sees a patient **only if** an active assignment row exists" and "**No FK pins an employee here** — assignment is per-session/enrollment." Per CLAUDE.md v3, `patient_assignments` is the "RLS backbone" and is the authoritative model. The two sections enforce assigned-patient visibility through two different mechanisms. Worse, the domain section (§N) says "employee-sees-only-assigned" without naming either. **Fix:** Enforce `patient_assignments` as the single source of truth. Rewrite `can_access_patient()` to `SELECT EXISTS(SELECT 1 FROM patient_assignments WHERE patient_id=p_patient AND employee_id=auth.uid() AND is_active)`. Do not gate visibility on `schedule_sessions` FK — use `patient_assignments` consistently across RLS, domain, and arch.

**2. [CRITICAL] Report visibility-flip enum/value mismatch across all four sections — the flip will silently fail.**
- Schema: `report_status` enum = `('draft','completed')`; flip event sets `visibility='staff_only'` and is keyed on `status='completed'`.
- RBAC: invents `report_status` enum = `('draft','saved')`; RLS predicate is `status='draft'` for employee read, `status='saved'` to hide; never references the schema's `visibility` column at all.
- Arch: says the RLS predicate is `status != saved/completed` (hedges both names).
- Domain (§E.7): uses `draft → saved → corrected` AND `draft → discarded`; assessment (§B.8) uses `draft → saved → corrected`.

So there are at least three different "completed" literals (`completed`, `saved`) and two extra states (`corrected`, `discarded`) that **do not exist in the schema enum**. Any policy written as `status='saved'` against a column constrained to `('draft','completed')` is a guaranteed runtime error or always-false. **Fix:** Canonicalize `report_status = ('draft','completed','corrected','discarded')` in the schema, decide whether the flip is driven by `status` *or* `visibility` (the schema has both — pick the `visibility` column as the RLS predicate since it is purpose-built, and have the trigger set it), and rewrite every RBAC/arch policy to that single contract.

**3. [CRITICAL] The `reports` table has both `status` and `visibility`, but the two designs disagree on which one RLS reads — creating a redundant, desync-prone pair.**
Schema defines BOTH `status report_status` and `visibility report_visibility` with a trigger setting `visibility='staff_only'` when `status='completed'`. RBAC's actual policies key only on `status`. If RLS reads `status` but the trigger also maintains `visibility`, the `visibility` column is dead weight that will drift (e.g., HR sets a row back to draft for correction → `status='corrected'` but `visibility` stale). **Fix:** Drop one column. Recommend keeping `status` as the lifecycle field and deriving employee visibility purely from `status IN ('draft')`; remove `report_visibility` and its enum, or vice-versa — but a single source of truth is mandatory for the headline "vanish on save" requirement.

**4. [CRITICAL] `profiles` table is defined twice with conflicting columns and enum name.**
- Schema: enum `user_role` = `('employee','admin','director')`; columns include `professional_license_no`, `ot_id_code`, `avatar_url`, `bio`, `nickname`, `is_active`, `deleted_at`.
- RBAC: enum `app_role` should be unified to `user_role` = `('employee','admin','director')` per v3; columns `license_no`, `photo_path` (different names), no `ot_id_code`/`nickname`/`bio`.

Every helper in RBAC (`auth_role()`, `custom_access_token_hook`, the JWT claim `app_role`) must use `user_role`, not a separate `app_role`. The schema's DDL creates `user_role` and `audit_logs.actor_role user_role`. `audit_capture()` must cast to `auth_role()` returning `user_role` and insert into `actor_role user_role` consistently. The design view (`patient_card`) references columns that **do not exist** on real patients (schema has no `age`, `patient_status`, `course_status` — those would live on their own tables). **Fix:** One `profiles` DDL, one role enum name (`user_role` with values `('employee','admin','director')`), reconcile column names (`license_no` vs `professional_license_no`, `photo_path` vs `avatar_url`), and fix all view/query references to use real columns and a single role enum.

**5. [CRITICAL] Director-edit-after-approval RLS predicate references a correction-status value that does not exist.**
- Schema/RBAC correction state machine: `pending → approved → applied`. RBAC's `ci_update` policy checks `cc.status = 'approved'`.
- Arch states Director check-in edits are "gated on **approved** correction status at RLS level" and "`correction_requests.status = 'approved'`".
- Domain must use the same literal: `approved` (pending → approved → applied).

All references must standardize on `approved` (the schema enum value) for the post-Director-approval, pre-Admin-apply state. The approval chain per v3: Director approves (status → `approved`) → Admin applies (status → `applied`). **Fix:** Standardize on `approved` (the schema enum value) everywhere across schema, RBAC, arch, and domain. Confirm no `owner_approved` or `approved_pending_apply` literals remain.

**6. [CRITICAL] `check_ins` status column referenced by RLS/views does not exist in the schema.**
The schema `check_ins` table has **no `status` column** — it has `kind`, `is_late`, `within_geofence`, `corrected`. But:
- RBAC `daily_insert` policy requires `EXISTS(... check_ins c WHERE ... c.status in ('on_time','late'))`.
- RBAC `apply_checkin_correction()` does `update check_ins set status = coalesce((c.requested_payload->>'status'), status)` and `set checked_in_at = ...` — neither `status` nor `checked_in_at` columns exist (schema uses `client_event_at`/`server_received_at`).
- The schema's own `course_progress` view and work-hours query instead derive countability from `schedule_sessions.status IN ('attended','late')`, not from `check_ins`.

Meanwhile domain §D.6 defines a rich check-in status machine (`pending/checked_in/checked_in_late/checked_out/no_checkin/skipped/...`) that lives on neither table cleanly. **Fix:** Decide where attendance status lives. The schema's model (status on `schedule_sessions`, evidence on `check_ins`) is sound; rewrite all RBAC policies/RPCs to gate on `schedule_sessions.status` and to edit `check_ins.client_event_at` (not `checked_in_at`/`status`). The `on_time` literal must become `attended` to match `session_status`.

**7. [HIGH] Session/enum literal mismatches between schema and domain/arch state machines.**
Schema `session_status = ('scheduled','attended','late','no_checkin','skipped','cancelled')`. Domain §F.7 introduces `in_progress`, `completed`, `rescheduled`, `corrected` as session states; §D.6 uses `checked_in`, `checked_in_late`, `checked_out`. None of these are in the enum. Arch uses `on_time` for check-in. **Fix:** Either extend `session_status` to include the lifecycle states the domain spec relies on (`in_progress`, `completed`, `rescheduled`, `corrected`) or map the domain's conceptual states onto the existing six and document the mapping. As written, code following the domain spec will insert invalid enum values.

**8. [HIGH] Director cap: "exactly 2 Director accounts" is contradicted within RBAC and unenforceable as written; also conflicts with schema.**
RBAC says "Director is exactly TWO accounts," provides a broken `create unique index ux_director_slot on profiles((role)) where role='director'` (a partial unique index on a constant expression allows only **one** director, not two — it would reject the 2nd director), then replaces it with a trigger capping at `> 2`. The trigger is `AFTER ... DEFERRABLE INITIALLY DEFERRED ... FOR EACH ROW` returning `null` — a row-level deferred constraint trigger returning null is fine, but the comment/index above it is actively wrong and would be copied. The schema section never caps directors. Per CLAUDE.md v3 §5, Director cap is hard-capped at exactly 2 accounts. **Fix:** Delete the unique-index line entirely (it caps at 1 and contradicts the 2-cap); keep only the count trigger. Add the cap to the schema section so it is not lost, and update the constraint to enforce `= 2`, not `<= 2`.

**9. [HIGH] Buddhist-era / timezone correctness gap in the "no-checkin nightly cron" and late calculation.**
Multiple sections store `timestamptz` UTC and compute `is_late = client_event_at > scheduled_start + late_threshold`. But `scheduled_start` is defined as "date+slot_start" — `work_hour_slots.slot_start` is a `time` with no zone, and `scheduled_date` is a `date`. Composing a UTC `timestamptz` from a Thai local date+time requires explicit `AT TIME ZONE 'Asia/Bangkok'`; nothing in the schema/derived-values section shows that conversion. If `scheduled_start` is naively built in UTC, every late/on-time/no-checkin decision is off by 7 hours, and the "nightly cron at day end" (§D, arch §5.3) will roll sessions to `no_checkin` at 07:00 Bangkok, not midnight. The Buddhist-era handling is correctly "display only" everywhere (good, consistent), but the **timezone** of derived comparisons is unspecified and will silently corrupt สาย/ไม่ได้เช็คอิน labeling — the exact thing the design treats as financially load-bearing. **Fix:** Specify that `scheduled_start = (scheduled_date + slot_start) AT TIME ZONE 'Asia/Bangkok'`, and that all day-boundary crons operate in `Asia/Bangkok`. Also note `kpi_evaluations.period_year` / `kpi_templates.period_year` are "Gregorian; พ.ศ. derived" — confirm dashboards/exports never group by a BE year, or year-boundary stats will be wrong.

**10. [HIGH] PWA offline check-in vs RLS/auth: the offline sync path cannot satisfy the RLS write policies it depends on.**
- Arch §4 has the client generate `check_ins.id = clientUuid` and the processor "call Server Action with the clientUuid idempotency key," with "server upserts on clientUuid (unique constraint)." But RBAC's `ci_insert` policy is `INSERT ... with check (employee_id = auth.uid() and is_enabled())` — an **INSERT** policy. An idempotent **upsert** (`ON CONFLICT DO UPDATE`) on replay becomes an UPDATE, which is governed by `ci_update` — and `ci_update` forbids employees entirely (`is_owner() OR (is_hr() AND approved-correction-exists)`). So a duplicate offline replay would attempt an employee UPDATE and be **rejected by RLS**, defeating the "safe retries / no-op" claim. **Fix:** Make replays a true no-op via `INSERT ... ON CONFLICT (id) DO NOTHING` executed through the SECURITY DEFINER check-in RPC (server-side, service role), not via the client respecting RLS. The arch already says check-ins go through a Server Action; make explicit that the insert/dedupe runs with elevated privilege and the RLS insert policy is defense-in-depth only.

**11. [HIGH] Offline gating contradiction: assessment/daily "require a check-in" but the check-in itself is offline-queued and not yet on the server.**
Domain §E.4/§B.5 and the schema CHECK constraint `report_type IN ('assessment_swallow','assessment_hand','daily') ⇒ check_in_id IS NOT NULL` require a FK to a persisted `check_ins.id`. Offline, the report is created before the check-in has synced, so `check_in_id` points to a client UUID not yet in the DB → the FK insert fails on sync if ordering isn't guaranteed, and the CHECK can't be satisfied with a null. Arch §4.7 hand-waves "enforced against the queued check-in (linkedCheckinUuid)." **Fix:** Because `check_ins.id` is the client UUID (good design choice), the report's `check_in_id` can be set to that same client UUID offline; the sync processor MUST upload the check-in before the dependent report (it says "oldest-first," but oldest report could precede the check-in in wall-clock only if the user checked in first — enforce explicit dependency ordering, not just timestamp ordering), or use a deferrable FK. State this dependency-ordered sync rule explicitly.

**12. [HIGH] Relatives portal auth model is mutually contradictory across sections, breaking its RLS.**
- Schema `relative_access`: `auth_user_id uuid FK→auth.users` **or** `access_token text`, with RLS "relative may read only their patient_id's…".
- RBAC §2 (relatives): "Relatives are **not** Supabase Auth users in v1 … data is read server-side with service role + an explicit relative_id filter," i.e., **no RLS for relatives, service-role only**.
- Arch: "token-link auth," `/relatives/portal/[token]`, RLS scopes the channel.
- Domain §J.1: "scoped link/account … RLS: relative sees only that patient's data."

If relatives are not auth users (RBAC's v1 choice), then `auth.uid()` is null in any relative request and **no RLS policy referencing `auth.uid()` can authorize them** — the schema's stated relative RLS is impossible, and the arch's "Realtime authorization uses RLS" for the relatives channel cannot work (Realtime needs an authenticated JWT). **Fix:** Commit to one model. Given the token-link UX everywhere, the consistent answer is: relatives are unauthenticated, all relative data access goes through server-side service-role reads filtered by the token→patient mapping (no Realtime for relatives, or issue a scoped anon JWT). Remove the schema's `auth.uid()`-based relative RLS claim and arch's "Realtime via RLS" for relatives, or actually make relatives auth users with a `relative` role (then add it to `user_role`, which currently has only 3 values).

**13. [HIGH] Audit log readability contradiction: schema says "admin scoped" can read; RBAC says Admin is explicitly excluded.**
- Schema `audit_logs`: "SELECT for director (+ admin scoped)" and matrix-free.
- RBAC §1 matrix and §2: "**audit_log: select: director only.** Admin explicitly excluded for separation of duties … Admin cannot read the audit log."
- Domain §L.2: "viewable by Admin (scoped) + director (full)."

Directly opposed (Admin can vs cannot read audit). This is a security-policy contradiction, not cosmetic. Per CLAUDE.md v3, audit logs are **Director-only read**. **Fix:** Decide per the separation-of-duties rationale (RBAC's director-only is the stronger, defensible stance given Admin is the most-audited actor) and correct schema and domain to match. Director must have unrestricted read; Admin has NO audit access in v1.

**14. [HIGH] `audit_logs` table name and shape differ between schema and RBAC.**
Schema: table `audit_logs`, PK `uuid`, columns `actor_role user_role`, `entity_table`, `entity_id uuid`, `before/after`, `occurred_at`. RBAC: table `audit_log` (singular), PK `bigint identity`, `actor_role user_role` (per v3 fix to #4), `entity` (not `entity_table`), `entity_id text`, `changed_cols`, `request_id`, `context`. The generic `audit_capture()` trigger inserts into `audit_log(...)` with `entity_id text` (`coalesce(v_after->>'id', v_before->>'id')`), but the schema's `entity_id` is `uuid` — bigint/text identity vs uuid PK, singular vs plural name. Triggers attached per the RBAC list will fail against the schema's table. **Fix:** One canonical audit table definition: use `audit_logs` (plural to match schema), `entity_id text` (polymorphic safety), and reconcile all RBAC/trigger inserts to this single shape.

**15. [MEDIUM] Course "session 9 alert" derivation is inconsistent and likely off-by-one with the bonus.**
Schema §5: alert when `used_sessions = total_sessions - 1` and comments "the 9th of a 10-pack incl. bonus." For `pkg_10_plus_1`, `total_sessions = 11`, so `total-1 = 10` → the alert fires at the **10th** completed session, not the 9th. The notification enum is literally `session_alert_9`. Domain §F.2/§F.7 says "Alert at session 9 (one before nominal end of a 10-course)." For a 10+1 pack, "nominal end" is ambiguous (10 paid, 11 delivered). So the alert name, the schema formula, and the domain intent disagree on whether 9 means "9th visit," "one before paid total (10→fires at 9)," or "one before grand total (11→fires at 10)." **Fix:** Define precisely against `base_sessions` vs `total_sessions`. If the requirement is "one before the paid course ends," fire at `used = base_sessions - 1` (=9 for a 10+1), independent of bonus. Rename or document `session_alert_9` accordingly and align the schema view's threshold.

**16. [MEDIUM] `course_progress` view counts via `check_ins` but the rest of the schema counts via `schedule_sessions.status`, producing two different "used" numbers.**
The schema's `course_progress` view does `count(ci.id) filter (where s.counts_as_training and s.status in ('attended','late'))` joining `check_ins ci ... kind='check_in'`. But a session can be `attended/late` with `counts_as_training=true` and still (edge) lack a `check_ins` row if status was set by correction/manual edit — then the count drops it. Conversely the work-hours query and §5 text say "a session counts only when a valid check-in exists AND status in (attended,late)." The relatives portal, alerts, and the `remaining_sessions` all read this view, while domain §F says counts come "from valid check-ins" and arch says Edge Functions "re-compute course progress from check_ins." The double condition (status AND check_in existence) is redundant if status is only ever set by the check-in flow — but corrections can set status without a check-in row, silently miscounting. **Fix:** Pick the single source of truth — recommend counting on `schedule_sessions.status IN ('attended','late') AND counts_as_training` only (drop the `check_ins` join in the view), since corrections update status; or guarantee corrections always maintain a `check_ins` row. Document so alerts/portal/remaining all agree.

**17. [MEDIUM] `is_enabled()` / deactivation guard is referenced but `is_active` semantics differ from JWT role path, and arch never wires deactivation check into Server Actions.**
RBAC correctly notes JWT claims are stale and adds `is_enabled()` (live `profiles.is_active`) ANDed into writes. But the arch/roadmap auth descriptions only mention "role claim" and never carry `is_enabled()` into Server Actions, and the schema's `profiles.is_active` exists but no section guarantees Server Actions re-check it (they re-check `getUser()` and role). Per CLAUDE.md v3 §9, deactivated users must be **forced sign-out** and every write via Server Action must re-check `is_enabled()`. A deactivated user with a live token could pass a Server Action that checks role-from-claim but not `is_enabled()`. **Fix:** Make "every mutating Server Action re-checks `is_enabled()` server-side (live DB check, not from JWT claim)" an explicit cross-cutting rule, matching the RLS `is_enabled()` AND.

**18. [MEDIUM] `kpi_templates` is referenced by a foreign key before it is defined, and KPI table/enum names diverge.**
`kpi_evaluations.template_id uuid references kpi_templates(id)` and the FK appears in the DDL list region while `kpi_templates` is described later as one of the "remaining tables… same scaffolding" without DDL. Ordered migration will fail unless `kpi_templates` is created first. Also domain/roadmap call it the "question bank" / `kpi_question_bank`; design/arch call it `kpi_templates`. RBAC matrix calls it `kpi_question_bank` with columns `year, is_active`; schema calls it `kpi_templates` with `period_year`. **Fix:** One name (`kpi_templates`), create it before `kpi_evaluations` in migration order, and reconcile `year` vs `period_year`.

**19. [MEDIUM] Booking default status conflicts.**
Schema `bookings.status` default `'booked'`. RBAC's `submit_public_booking` RPC "inserts with status `awaiting_payment`/`booked`." Domain §A.6 makes it conditional on payment-pending config. Design uses `booked` default. Minor, but the public RPC and the column default must agree or the RPC's explicit value silently overrides the documented default behavior. **Fix:** State that the RPC sets status explicitly from config and that the column default is a fallback only.

**20. [MEDIUM] `force row level security` + service-role assumption needs a caveat.**
RBAC enables `force row level security` on every table "so even the table owner is constrained," then says "service role still bypasses." `FORCE RLS` does **not** exempt the `service_role`/`bypassrls` role automatically — `BYPASSRLS` is what exempts it, and `FORCE` specifically makes policies apply even to the table owner. Supabase's `service_role` has `bypassrls`, so it is fine, but the audit-capture and other SECURITY DEFINER functions run as their *definer* (table owner), and with `FORCE RLS` on, a SECURITY DEFINER function owned by the table owner will now be subject to RLS on that table — which can break `audit_capture()` inserting into `audit_log` and the role-helper reads. **Fix:** Confirm SECURITY DEFINER helpers are owned by a `BYPASSRLS` role (or the functions explicitly `SET row_security = off` where appropriate), and verify `can_access_patient()`/`auth_role()` still bypass under `FORCE RLS`. As written, `FORCE` + SECURITY DEFINER owned by a non-bypass role is a latent breakage.

**21. [MEDIUM] `patients` PHI masking view ordering and column drift will not compile.**
Beyond the `bbc_cn`/`age`/`patient_status`/`course_status` name errors (item 4), the `patient_card` view applies a regex mask on `national_id` assuming 13 digits formatted `\d{1}...\d{4}`, but the schema stores `national_id text` with no format guarantee (and intake may store dashes). If the value already contains dashes or is non-numeric, the regex passes the raw value through unmasked — a PHI leak. **Fix:** Normalize/validate `national_id` on write, and make the mask fail-closed (mask anything not matching the expected pattern rather than returning it raw).

**22. [LOW] Notification audience/type vs relatives-not-auth-user.**
`notification_audience` includes `relative` and `notifications.recipient_relative_id FK→relatives`, consistent. But channels include `push` while relatives (non-auth, token-link) cannot receive web push without a subscription/auth context; arch lists relative notifications as in-app/email/LINE. Minor consistency note. **Fix:** Restrict `push` audience to staff/employee, or document how an unauthenticated relative obtains a push subscription.

**23. [LOW] `gender` enum vs intake free-text, and `consciousness` enum unused.**
Schema defines `consciousness` enum but the Hand Function assessment stores consciousness inside `payload` jsonb (domain §B.4), so the enum is never used by a column — dead type. `diagnosis_category` enum is duplicated as both a `patients` column and a `diagnoses.category` lookup, which is fine, but `patients` ER text says "patients *──1 diagnoses (via diagnosis_category)" implying a join that has no FK (it's an enum match, not a relation). **Fix:** Drop unused `consciousness` enum (or use it), and correct the ER prose to not imply a FK relationship that doesn't exist.
